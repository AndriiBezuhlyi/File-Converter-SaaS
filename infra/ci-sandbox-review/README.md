# Disposable sandbox VM: technical review only

**Not an implemented fix. Do not provision, load a policy, register a runner or wire this into Actions without separate approval.** No existing test or production configuration is changed. `vm.yaml` is a review specification, not a deployable provider manifest. The immutable OS image, Docker version and provider identity are intentionally unresolved: no account, region or budget has been approved.

## Evidence and cause

- Original hosted run [43519896030](https://github.com/AndriiBezuhlyi/File-Converter-SaaS/actions/runs/43519896030), Ubuntu 24.04: all four Linux smoke tests failed before conversion.
- Approved diagnostic commit `4e2e070`, run [43521533855](https://github.com/AndriiBezuhlyi/File-Converter-SaaS/actions/runs/43521533855): `ubuntu-latest` actually selected Ubuntu 26.04 image `20261111.196.1`. The minimal probe reproduced `bwrap: Failed to make / slave: Permission denied`; label `docker-default (enforce)`, all capability masks zero, `NoNewPrivs=1`, `Seccomp=2`. No matching bwrap kernel audit event was emitted; do not invent one.
- The checked-in seccomp profile allows `clone`, `unshare`, `mount`, `umount2` and `pivot_root`. Bubblewrap reaches its recursive slave-propagation mount after namespace creation; Docker's default AppArmor profile explicitly denies mount. This is outer AppArmor mount mediation, not a conversion failure. Adding an outer capability does not override an AppArmor denial.
- Local Docker Desktop/WSL has AppArmor disabled. The exact minimal probe and all four unchanged tests pass there. That verifies the existing seccomp/cgroup/sandbox combination, not the proposed AppArmor policy.

## Concrete candidate and permissions

`vm.yaml` specifies a single Ubuntu 24.04 amd64 VM, 2 vCPU, 8 GiB RAM, 30 GiB disposable disk and a hard 30-minute provider-side expiry. No public ingress, instance role, repository credential or production secret. Provider-specific private management must be selected before this can run. No GitHub runner is installed. A GitHub-hosted controller would transfer a reviewed worker image plus unchanged tests, verify SHA-256, execute once and destroy the VM. All other CI jobs stay hosted. The candidate is manual-only, protected-environment approved and bound to a maintainer-reviewed commit SHA; never accept a PR ref or execute a `pull_request_target` checkout.

Exact proposed test invocation, **only inside the approved disposable guest after profile validation/approval**, from the transferred artifact root:

```sh
docker run --rm --init --read-only --network none \
  --cpus 1 --memory 1g --pids-limit 128 --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --security-opt seccomp=infra/security/worker-seccomp.json \
  --security-opt apparmor=flux-ci-bwrap-review \
  --tmpfs /tmp:rw,nosuid,nodev,size=256m,mode=1777 \
  --mount "type=bind,source=$PWD/apps/backend/test,target=/app/apps/backend/test,readonly" \
  flux-ci-worker:local node --test --test-concurrency=1 \
    test/conversion-engine.linux.mjs test/engine-crash.linux.mjs
```

`flux-ci-bwrap.apparmor` is an **unapplied candidate**, based on Docker's baseline filesystem/proc/sys restrictions with narrower network permissions. It is not yet proven sufficient or minimal by runtime audit. Unlisted mounts remain denied by default; there is no bare `mount,` permission and no unconfined transition. Permission rationale:

| Addition                                                              | Purpose                                                                       | Limit/risk                                                                                                                                                                                                                                            |
| --------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1 `userns`                                                           | Permit nested unprivileged user namespaces without changing sysctls           | Exposes namespace kernel surface to this container; outer capability masks must remain zero                                                                                                                                                           |
| A2 recursive slave propagation at `/`                                 | Prevent sandbox mount changes propagating outward                             | Namespace propagation permission; no host mount namespace membership permitted                                                                                                                                                                        |
| A3 tmpfs/proc/devpts at staging destinations                          | Empty sandbox root, bounded work area, private proc/device view               | Filesystem types and paths constrained; cgroup/rlimit/tmpfs budgets still mandatory                                                                                                                                                                   |
| A4 selected bind sources, staging destinations and read-only remounts | Present runtime libraries, synthetic input and devices; seal mounts read-only | Brief staging mounts exist before remount; an AppArmor allow does not make them read-only. Existing bwrap implementation and assertions remain required. Input paths under `/oldroot/tmp/**` cover test-generated scratch, not arbitrary host uploads |
| A5 two root pivots, no profile transition                             | Discard the old root during bwrap setup                                       | Keep the same enforcing label through pivot and exec; verify actual kernel-resolved paths before approval                                                                                                                                             |

`file`, `capability`, same-profile signal/ptrace and `umount` are baseline-style permissions, not added outer capabilities. `network unix` permits local IPC; `network netlink` permits private loopback setup. Neither overrides `--network none` or per-attempt `--unshare-all`. The profile must not be used for the networked production worker or the live stack without a separate design/review. Mount paths/remount options are version-sensitive; unexpected denials require evidence and review, never broad automatic widening. The minimal CI probe's broad `--ro-bind / /` is intentionally **not** authorized by this narrower candidate; use a restricted probe with the production runtime binds when validating it, then run all existing tests unchanged.

## Verification gate before any integration

1. After separate approval, create only the dedicated VM. Assert AppArmor enabled/enforcing, cgroup v2, expected Docker/kernel/bwrap versions and unprivileged user namespace availability without modifying host sysctls. Record immutable image and tool versions.
2. Compile the profile without loading it (`apparmor_parser --skip-kernel-load --skip-read-cache ...`). Loading it in the disposable guest requires explicit approval. Never replace `docker-default`; assign the named profile only to the test container.
3. Run restricted capability/namespace probes and inspect outer and inner AppArmor labels, seccomp mode, `NoNewPrivs`, zero capability masks, distinct user/mount/PID/network namespace identities and UID/GID maps. Check actual cgroup files: CPU quota/period <= 1, memory <= 1 GiB, pids <= 128. Inspect read-only root, 256 MiB outer tmpfs and 128 MiB per-attempt tmpfs; preserve existing rlimits.
4. Verify negative probes: mount outside staging, unauthorized pivot, access to service sentinel/other attempt/host root, root/dev writes, network egress, and prohibited syscalls must fail. A successful `/bin/true` is insufficient. Audit denied mount operations where available; do not mark unavailable diagnostics as isolation proof.
5. Run both existing files unchanged: `conversion-engine.linux.mjs` and `engine-crash.linux.mjs`. Require four passes, zero skips, real JPG/PNG/DOCX conversion, malformed input rejection, credential/filesystem/network isolation, disk exhaustion, 60-second deadline and descendant cleanup. Capture only synthetic fixture results; no production services or credentials.
6. Destroy VM, attached disks, interfaces and temporary rules even after failure/cancellation. An independent provider-side TTL reaper must cover a lost controller. A guest shutdown or `--ephemeral` runner flag is not destruction. Require provider confirmation of removal before declaring the verification complete.
