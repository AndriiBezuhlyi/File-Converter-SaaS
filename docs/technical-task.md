# Senior Project — File Converter SaaS

## 1. Project Overview

Цей продукт призначений для конвертації файлів. У майбутньому він повинен легко масштабуватися, наприклад, повинна бути можливість додавати нові формати файлів, нові напрямки конвертації та додаткові функції без значних змін основної логіки застосунку.

Базово він повинен мати функції реєстрації, авторизації та всі основні можливості, пов'язані з управлінням акаунтом користувача.

Також повинні бути доступні конвертація файлів (завантаження та скачування), збереження файлів у своєму акаунті, їх видалення та можливість керувати автоматичним збереженням.

Гість може безкоштовно виконати одну успішну конвертацію одного файлу без реєстрації. Для наступних конвертацій потрібно увійти або створити акаунт. Авторизація не означає оплату: платні тарифи залишаються поза MVP.

## 2. File Conversion

Підтримувані формати:

- PNG ↔ JPG.
- DOCX ↔ PDF (для початку можна реалізувати лише DOCX → PDF).

Якщо файл занадто великий, не відповідає вибраному формату, пошкоджений або виникла інша проблема, потрібно показати зрозумілу користувачеві помилку.

Максимальний розмір файлу — 20 МБ.

Сервер повинен перевіряти реальний тип вмісту, розмір і допустимість файлу, а не тільки його розширення.

Під час завантаження файлу потрібно показувати реальний прогрес у відсотках. Під час самої конвертації — індикатор виконання, а якщо можливо отримати реальний прогрес, то відображати його у відсотках.

Після успішного завершення конвертації потрібно показати галочку та надати можливість скачати файл.

## 3. Pages & UI

### Головна сторінка

На головній сторінці найбільша увага повинна приділятися самому конвертеру.

Користувач повинен мати можливість:

- Перетягнути файл у спеціальну область (drag & drop).
- Вибрати файл через файловий менеджер пристрою.
- Вибрати необхідний формат конвертації.
- Запустити конвертацію та скачати результат.

Нижче повинна бути покрокова інструкція з користування конвертером.

Перша успішна конвертація доступна безкоштовно без реєстрації та входу. Гість може вибрати файл і цільовий формат та запустити конвертацію без модального вікна авторизації. Біля конвертера показувати: «1 файл безкоштовно без реєстрації».

Після використання пробної можливості наступне натискання «Конвертувати» відкриває модальне вікно: «Безкоштовну конвертацію вже використано. Увійдіть або створіть акаунт, щоб продовжити». Для цієї наступної конвертації файл не завантажується до входу. Після входу вибір зберігається в пам'яті, якщо сторінка не перезавантажувалася; після втрати файлу через навігацію чи перезавантаження потрібно запропонувати вибрати його повторно.

Ліміт перевіряється на сервері за захищеним гостьовим ідентифікатором браузера. Одна прийнята активна задача резервує можливість; успішне завершення витрачає її, а відхилення файлу чи остаточна помилка конвертації — ні. Технічні повторні спроби утримують резерв. Паралельне створення другої активної гостьової задачі заборонене. Оновлення сторінки та завершення терміну доступності результату не відновлюють ліміт. Це облік браузерного контексту, а не гарантоване визначення людини: інший браузер або очищення cookies можуть обійти його; передбачити додаткові обмеження частоти запитів.

Перевірка статусу та повторне завантаження готового гостьового результату не вимагають входу і не витрачають додаткових спроб протягом строку доступності.

### Сторінка профілю / акаунту

Повинна містити основні дані користувача, окрім пароля у відкритому вигляді.

Повинна бути можливість змінювати особисті дані та пароль із відповідним підтвердженням особи.

Також повинні бути налаштування конвертації та збереження файлів.

На сторінці повинна бути кнопка «Мої файли», яка переводитиме на окрему сторінку зі збереженими файлами.

На цій сторінці повинен відображатися унікальний API-ключ з можливістю копіювання, приховування та випуску нового ключа. Після випуску нового ключа старий повинен деактивуватися.

### Сторінка «Мої файли»

На цій сторінці повинен бути список збережених файлів із можливістю:

- Сортування за датою (останні файли).
- Фільтрації за типом файлу.
- Пошуку за назвою.
- Скачування файлу.
- Видалення файлу.
- Перегляду додаткової інформації про файл.

Також повинен бути toggle для ввімкнення та вимкнення автоматичного збереження сконвертованих файлів.

Це налаштування повинно бути синхронізоване з налаштуваннями в профілі.

Вимкнення автоматичного збереження не повинно видаляти вже збережені файли.

Якщо файлів немає, потрібно показувати відповідне повідомлення замість порожнього списку.

### Сторінки реєстрації, авторизації та відновлення пароля

Повинні бути окремі інтерфейси для створення акаунту, входу та відновлення доступу.

У формах потрібно передбачити валідацію полів і зрозумілі повідомлення про помилки.

### Сторінка API Documentation

Повинна містити чітку інструкцію щодо використання API сторонніми сайтами та розробниками.

Необхідно описати спосіб авторизації через API-ключ, доступні операції, параметри запитів, приклади використання та можливі помилки.

## 4. Authentication & Users

Реєстрація через електронну пошту або номер телефону.

Якщо реєстрація відбувається через електронну пошту, потрібно підтвердити її через повідомлення на пошту.

Якщо через номер телефону, можна розглянути підтвердження через Telegram з відповідною перевіркою належності акаунту користувачу.

Можливо також використати обидва варіанти, наприклад:

Пошта як основний метод реєстрації та підтвердження, а номер телефону і Telegram як додатковий метод.

Відновлення пароля також одним із цих двох варіантів.

Для першої версії достатньо реалізувати реєстрацію, авторизацію та відновлення пароля через електронну пошту.

## 5. API

Потрібен загальний API, який дозволятиме іншим сайтам і розробникам використовувати сервіс конвертації файлів.

Повинна бути адреса API, на яку можна надсилати файли та отримувати відповідь від сервера.

Операції конвертації через публічний API виконуються лише в тому випадку, якщо до запиту додано дійсний унікальний API-ключ.

Якщо ключ відсутній, неправильний або деактивований, сервер повинен повертати відповідну помилку.

Файли, сконвертовані через API, можуть зберігатися в профілі користувача залежно від налаштувань автоматичного збереження.

У разі помилки конвертації користувач повинен отримувати зрозуміле повідомлення залежно від причини проблеми.

Детальний API-контракт, endpoints, формати запитів і відповідей та технічний механізм роботи API визначені в окремому блоці рекомендацій AI.

## 6. File Storage

Потрібно реалізувати систему збереження сконвертованих файлів з можливістю керування ними через особистий кабінет.

Збережені файли доступні тільки власнику акаунту. Гостьова задача та її тимчасовий результат доступні лише за відповідним захищеним гостьовим токеном; знання URL чи ідентифікатора задачі недостатньо. Гостьові результати доступні 1 годину після успішного завершення й не додаються автоматично до «Моїх файлів», зокрема після входу.

Якщо автоматичне збереження вимкнене, сконвертований файл повинен залишатися доступним для скачування протягом певного обмеженого часу, після чого видалятися автоматично.

При видаленні файлу користувачем він повинен ставати недоступним для подальшого скачування.

Конкретні технології зберігання та управління файлами визначені в блоці AI.

## 3. Architecture

Рекомендована архітектура — modular monolith із окремим conversion worker.

Основні модулі backend:

- Auth — реєстрація, авторизація, відновлення пароля та обмежений гостьовий контекст.
- Users — профілі та налаштування користувачів.
- API Keys — створення, відкликання та перевірка ключів.
- Conversions — створення та відстеження задач конвертації.
- Files — робота з файлами та їх метаданими.
- Storage — взаємодія з об'єктним сховищем.
- Notifications — email-підтвердження та службові повідомлення.

Frontend та сторонні API-клієнти використовують спільну бізнес-логіку конвертації.

Frontend використовує сесію користувача або обмежений гостьовий токен для однієї пробної конвертації. Гостьовий токен дозволяє лише створення пробної задачі, перевірку її статусу та завантаження відповідного результату. Профіль, налаштування, «Мої файли» та управління API-ключами потребують сесії користувача. Сторонні клієнти використовують API-ключ; гостьовий сценарій не замінює його для інтеграцій.

Вебсесія та окремий гостьовий токен повинні використовувати Secure, HttpOnly та відповідний SameSite cookie. Для запитів із cookies, які змінюють дані, зокрема гостьових, необхідно передбачити захист від CSRF. Хеш гостьового токена, стан пробної можливості та резерв активної задачі зберігати в PostgreSQL; втрата Redis-сесій не відновлює використану можливість.

Для API-ключів потрібно використовувати криптографічно стійку генерацію. На сервері зберігати лише захищений хеш ключа, а повний ключ показувати користувачу один раз під час створення або перевипуску.

## 4. API Contract

Базовий URL:

`/api/v1`

API повинен працювати через HTTPS.

### Authentication

Для сторонніх клієнтів endpoints конвертації та отримання результатів використовують заголовок:

`X-API-Key: YOUR_API_KEY`

API-ключ повинен передаватися тільки в HTTP-заголовку, не в URL.

### Endpoints

| Method | Endpoint                         | Description                     |
| ------ | -------------------------------- | ------------------------------- |
| POST   | /api/v1/conversions              | Створення задачі конвертації    |
| GET    | /api/v1/conversions/:id          | Отримання статусу задачі        |
| GET    | /api/v1/conversions/:id/download | Отримання сконвертованого файлу |
| GET    | /api/v1/files                    | Отримання збережених файлів     |
| GET    | /api/v1/files/:id                | Інформація про файл             |
| GET    | /api/v1/files/:id/download       | Завантаження збереженого файлу  |
| DELETE | /api/v1/files/:id                | Видалення файлу                 |

Endpoints із цього списку перевіряють API-ключ для сторонніх клієнтів або сесію користувача для власного frontend. Для першої пробної конвертації власний вебінтерфейс також може використовувати гостьовий токен на `POST /conversions`, `GET /conversions/:id` та `GET /conversions/:id/download`. Створення перевіряє ліміт, а статус і завантаження — належність задачі гостю. Гостьовий токен не приймається на `/files` та account endpoints. Наявний недійсний API-ключ не дозволяє переключитися на сесію чи гостьовий режим.

Для вебінтерфейсу передбачити `POST /api/v1/guest-session`: створення або відновлення гостьового контексту через захищену cookie; відповідь містить стан можливості (`available`, `reserved`, `consumed`) та активну задачу за наявності, але не секрет токена. Повторне звернення з чинним токеном не скидає ліміт. Деталі визначені в [архітектурі](architecture.md#guest-trial-policy).

Операції перегляду та видалення файлів завжди перевіряють, що файл належить авторизованому користувачу.

### POST /api/v1/conversions

Тип запиту:

`multipart/form-data`

Поля запиту:

- file — файл для конвертації.
- targetFormat — бажаний вихідний формат (jpg, png або pdf).

Сервер сам визначає вихідний тип файлу та перевіряє, чи підтримується відповідна конвертація.

Успішна відповідь:

HTTP 202 Accepted

```json
{
	"id": "conversion_123",
	"status": "queued",
	"sourceFormat": "jpg",
	"targetFormat": "png",
	"createdAt": "2026-10-13T18:00:00Z"
}
```

### GET /api/v1/conversions/:id

Повертає інформацію про поточний стан задачі.

Можливі статуси:

- queued — очікує обробки.
- processing — виконується конвертація.
- completed — успішно завершено.
- failed — сталася помилка.

Приклад:

```json
{
	"id": "conversion_123",
	"status": "completed",
	"downloadUrl": "/api/v1/conversions/conversion_123/download",
	"expiresAt": "2026-10-13T19:00:00Z"
}
```

`downloadUrl` не є відкритим публічним посиланням. Потрібна сесія власника, API-ключ власника або відповідний гостьовий токен. Для MVP файл передається через endpoint застосунку з перевіркою доступу, без відкритого URL сховища.

Для MVP frontend може перевіряти статус через polling кожні 1–2 секунди, доки задача не перейде у фінальний стан.

### GET /api/v1/conversions/:id/download

Після завершення конвертації повертає результат як файл із коректними заголовками Content-Type та Content-Disposition.

Файл може бути отриманий тільки власником відповідної задачі: користувачем акаунту або гостем із відповідним токеном. Витрачений пробний ліміт блокує нову гостьову конвертацію, але не статус чи завантаження наявного результату до його завершення строку доступності.

Якщо задача не завершена, сервер повертає відповідну помилку. Якщо термін зберігання файлу закінчився — повідомляє, що результат більше недоступний.

### Error Responses

Помилки повинні мати єдиний формат:

```json
{
	"error": {
		"code": "FILE_TOO_LARGE",
		"message": "The uploaded file exceeds the allowed size."
	}
}
```

Рекомендовані HTTP-статуси:

- 400 Bad Request — неправильні параметри.
- 401 Unauthorized — відсутні або недійсні облікові дані; `GUEST_CONVERSION_LIMIT_REACHED` — пробну можливість використано, для нової конвертації потрібен вхід.
- 409 Conflict — `GUEST_CONVERSION_IN_PROGRESS`: гостьова задача вже очікує або виконується; повторний запит не створює дубль.
- 403 Forbidden — недостатньо прав.
- 404 Not Found — ресурс відсутній або недоступний користувачу.
- 413 Payload Too Large — файл перевищує ліміт.
- 415 Unsupported Media Type — непідтримуваний формат.
- 422 Unprocessable Content — пошкоджений файл або неможлива конвертація.
- 429 Too Many Requests — перевищення ліміту запитів.
- 500 Internal Server Error — непередбачена серверна помилка.
- 503 Service Unavailable — тимчасова недоступність сервісу.

Необхідно розмежовувати помилки створення задачі та помилки, що виникли під час асинхронної конвертації. Якщо задача вже прийнята, її помилка відображається через статус `failed` із відповідним кодом.

### API Keys

У MVP користувач має один активний API-ключ.

Можливості:

- Створення ключа.
- Копіювання під час першого показу.
- Перевипуск ключа з негайною деактивацією попереднього.
- Перевірка валідності ключа на сервері.
- Зберігання хешу ключа, а не його відкритого значення.

Управління ключами здійснюється через захищені endpoints профілю, доступні лише за вебсесією користувача з додатковим підтвердженням особи для чутливих операцій.

Не дозволяти публічному API-ключу створювати інші API-ключі або змінювати пароль користувача.

## 5. File Storage Rules

- Зберігати файли у приватному Object Storage.
- Зберігати в PostgreSQL лише метадані, а не самі файли.
- Кожен файл повинен мати унікальний ідентифікатор та рівно одного власника: акаунт або гостьовий контекст.
- Не використовувати оригінальні назви файлів як ключі сховища.
- Файли повинні бути недоступні іншим користувачам і гостям.
- Гостьові результати завжди тимчасові: 1 година після успішного завершення, без автозбереження. Вхід не переносить їх до акаунту автоматично; збережений гостьовий контекст забезпечує доступ до завершення строку.
- Очищення результату не скидає використану пробну можливість. Гостьовий токен має залишатися чинним щонайменше до завершення доступності прийнятої задачі та результату.
- При вимкненому автоматичному збереженні результати зберігаються тимчасово протягом 1 години.
- При ввімкненому автоматичному збереженні результат додається до «Моїх файлів».
- Зміна налаштування збереження не впливає на раніше збережені файли.
- Видалення файлу користувачем робить його недоступним негайно та запускає очищення об'єкта у сховищі.
- Необхідно очищати тимчасові файли та результати невдалих задач.
- Врахувати можливість розбіжностей між базою даних та сховищем і передбачити повторне очищення.

## 6. Non-functional Requirements

### Security

- Використовувати HTTPS.
- Хешувати паролі за допомогою Argon2id.
- Перевіряти реальний тип файлів, а не тільки їх розширення.
- Перевіряти дозволені формати та розміри на сервері.
- Захищати доступ до файлів перевіркою власника.
- Встановити rate limiting для API.
- Ізолювати процеси конвертації.
- Не виконувати макроси та інший активний вміст документів.
- Обмежувати використання CPU, пам'яті, диска, часу виконання та кількості одночасних конвертацій.
- Не передавати секрети, паролі та API-ключі у логи.
- Забезпечити безпечну обробку тимчасових файлів.

### Performance

- Рекомендований початковий ліміт файлу — 20 МБ.
- Підтримувати асинхронну обробку через чергу.
- Не блокувати основний HTTP-сервер під час конвертації.
- Цільова швидкість JPG → PNG для звичайного файлу 5 МБ — до 10 секунд у визначеному тестовому середовищі.
- Передбачити timeout для задач і максимальну кількість одночасних worker-процесів.

### Reliability

- Помилка однієї задачі не повинна зупиняти інші задачі.
- Повторні спроби дозволені для тимчасових технічних помилок, але не для невалідних файлів.
- Усі задачі повинні мати статус і журнал діагностики.
- Потрібно передбачити автоматичне очищення невдалих та прострочених задач.

### Scalability

- Додавання нових форматів повинно виконуватися через окремі модулі/адаптери конвертації.
- Основна бізнес-логіка не повинна залежати від конкретного конвертера.
- Conversion workers повинні масштабуватися незалежно від API-сервера.

### Usability

- Адаптивний інтерфейс для desktop, tablet та mobile.
- Зрозумілі повідомлення про помилки.
- Індикатори завантаження та обробки.
- Доступність основних функцій із клавіатури.
- Передбачувана поведінка при втраті інтернет-з'єднання.

## 7. Testing & Acceptance Criteria

### Unit Tests

Перевірити:

- Валідацію форматів та розмірів.
- Визначення підтримуваних напрямків конвертації.
- Логіку автоматичного збереження.
- Гостьовий ліміт: резервування, використання після успіху, звільнення після остаточної помилки та збереження резерву під час повторних спроб.
- Перевірку API-ключів.
- Переходи між статусами задач.

### Integration Tests

Перевірити:

- Взаємодію backend із PostgreSQL.
- Роботу файлового сховища.
- Створення та обробку задач BullMQ.
- Роботу API при правильному та неправильному ключі.
- Перевірку прав доступу до файлів.
- Атомарне резервування гостьового ліміту при паралельних запитах, ідемпотентне завершення та відновлення після збою worker.
- Ізоляцію гостьових задач і відмову гостьовому токену на account/files endpoints.

### End-to-End Tests

Перевірити основні сценарії:

1. Реєстрація → підтвердження email → вхід.
2. Завантаження JPG → конвертація PNG → скачування.
3. Завантаження DOCX → конвертація PDF → скачування.
4. Увімкнення автоматичного збереження → конвертація → відображення у «Моїх файлах».
5. Вимкнення автоматичного збереження → конвертація → відсутність нового файлу у списку збережених.
6. Видалення файлу → повторне скачування недоступне.
7. Створення API-ключа → успішний зовнішній API-запит.
8. Перевипуск API-ключа → старий ключ більше не працює.
9. Надсилання файлу з неправильним розширенням або пошкодженим вмістом → очікувана помилка.
10. Спроба отримати чужий файл → доступ заборонено.
11. Гість → одна успішна конвертація → завантаження без реєстрації.
12. Наступна гостьова конвертація → вхід/реєстрація до завантаження нового файлу; після входу конвертація доступна за правилами акаунту.
13. Невалідний файл або остаточна помилка гостьової задачі → пробна можливість знову доступна з урахуванням rate limiting.
14. Паралельні запити гостя → прийнято не більше однієї активної задачі; після успіху ліміт не відновлюється при перезавантаженні чи очищенні результату.
15. Інший гостьовий токен → статус і результат чужої задачі недоступні; власний результат можна завантажувати повторно до завершення 1 години.
16. Вхід після гостьової конвертації → старий результат доступний через чинний гостьовий контекст до завершення строку і не додається автоматично до «Моїх файлів».

### Definition of Done

Функція вважається завершеною, якщо:

- Реалізовано описану поведінку.
- Є обробка помилок та нестандартних ситуацій.
- Виконуються необхідні автоматизовані тести.
- Не виявлено критичних проблем безпеки.
- Код проходить lint та typecheck.
- API-документація відповідає фактичній реалізації.
- Функція перевірена у локальному середовищі.

## 8. Implementation Strategy for Codex

Не реалізовувати весь застосунок одним великим кроком.

Розділити роботу на етапи:

1. Створити структуру проєкту та налаштувати інструменти.
2. Реалізувати базу даних, користувачів, авторизацію та серверний облік гостьової пробної конвертації.
3. Реалізувати backend-логіку конвертації JPG ↔ PNG.
4. Додати чергу задач та conversion worker.
5. Додати конвертацію DOCX → PDF.
6. Реалізувати Object Storage та управління файлами.
7. Реалізувати публічний API та управління API-ключами.
8. Створити сторінки frontend та інтегрувати їх із backend.
9. Створити API Documentation.
10. Додати тестування, перевірку безпеки та підготувати застосунок до розгортання.

Після кожного етапу запускати відповідні тести та перевіряти працездатність реалізованого функціоналу.

Не змінювати погоджений API-контракт або основні архітектурні рішення без явного пояснення необхідності змін.
