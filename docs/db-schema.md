# Database Schema

PostgreSQL 18 with Prisma 7. The source model is [schema.prisma](../apps/backend/prisma/schema.prisma); migration history is [prisma/migrations](../apps/backend/prisma/migrations). API/worker share the runtime Prisma/pg provider. Authentication/profile transactions, notification intents, guest credentials and guest-trial transaction helpers are implemented; conversion/file/settings/API-key services remain pending. No existing environment is migrated automatically.

## Models and relationships

| Model               | Purpose and important fields                                                                                                                                                                                                                             |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `User`              | UUID, normalized unique email, password hash, optional verified timestamp/display name and nonnegative session version.                                                                                                                                  |
| `UserSettings`      | One row per user, with `userId` as PK/FK and an `autoSave` boolean. Default is false; registration must create this row in its user-creation transaction. The FK does not require every user to have a settings row.                                     |
| `VerificationToken` | User-bound hash, purpose (`email_verification`, `password_reset`, `email_change`), expiry, consumption timestamp and attempt counter. Email changes also store the normalized pending destination.                                                       |
| `ApiKey`            | User-bound unique lookup prefix, protected secret hash, creation/revocation timestamps. Only one unrevoked key per user.                                                                                                                                 |
| `GuestSession`      | Unique opaque-token hash, credential expiry, durable `available/reserved/consumed` state, optional reservation FK and consumed timestamp. No dummy account is needed.                                                                                    |
| `File`              | Exactly one user or guest owner, unique private object key, display filename, detected format/MIME, byte size, input/output purpose, saved/temporary retention, expiry and soft/physical deletion metadata. File bytes remain in private object storage. |
| `Conversion`        | Exactly one owner, unique source and optional unique result FK, source/target formats, public state, immutable `saveResult` snapshot, safe error code, attempts, processing version, lease and lifecycle timestamps.                                     |
| `BackgroundTask`    | Durable conversion dispatch, file deletion, email notification or cleanup intent. Typed resource UUID, unique deduplication key, versioned JSON object, availability, attempts, lease, safe error code and completion time.                              |

Users own settings, credentials, files and conversions. Guests own files/conversions and may reserve one of their own conversions. Files can serve as one conversion's input or one published result. Background task resource identifiers are intentionally polymorphic; they are not foreign keys. User web-session records remain in Redis.

All IDs use native PostgreSQL UUIDs generated by `gen_random_uuid()`. Timestamps use `timestamptz(3)`; clients should exchange UTC ISO timestamps. `sizeBytes` is PostgreSQL `bigint` / Prisma `BigInt`: map it explicitly to a bounded JSON-safe API value rather than serializing Prisma records. Prisma maintains `@updatedAt` during ORM updates; raw SQL writers must set `updatedAt` themselves. Public DTOs must omit hashes, object keys, leases and other internal fields.

## Database-enforced invariants

The first migration creates the Prisma representation. The second adds SQL checks, partial indexes and PL/pgSQL guards that Prisma 7 cannot fully represent. The third adds the approved nonnegative `User.sessionVersion` with default zero. All migrations are transactional. Keep custom objects in later migrations; schema validation or client generation alone does not validate them.

- Emails are stored trimmed/lowercase and unique; hashes and key prefixes cannot be empty. Tokens require positive lifetimes, nonnegative attempts and a pending email only for email-change purpose. These checks do not implement token consumption, expiry authorization or password hashing.
- `File` and `Conversion` enforce `userId XOR guestSessionId`. Conversion inputs/results must match owner, purpose and format. A nullable multi-column FK alone would skip checks under PostgreSQL `MATCH SIMPLE`, so explicit guards validate both principal types. Referenced owner/type/retention fields are immutable; output expiry cannot later be extended. Conversion ownership, source, direction and auto-save snapshot are immutable too. IDs and existence checks do not replace request authorization.
- Only JPG → PNG, PNG → JPG and DOCX → PDF are accepted. MIME metadata must match the recorded format and sizes must be positive. Actual byte inspection, upload/output limits and resource-expansion limits belong to backend validation, not these metadata checks.
- Guests cannot save results. Saved files must be account-owned outputs without expiry. Temporary outputs require expiry; inputs are temporary and may use a separately configured cleanup deadline. Result retention must match the conversion's acceptance snapshot, with temporary expiry after completion. The service must set the required one-hour output deadline; the database does not invent a global input-cleanup lifetime.
- Conversion state shapes distinguish queued, processing, completed and failed jobs. Processing needs a complete lease and start timestamp; completion needs a result and completion timestamp; failure needs an error and failure timestamp. Terminal jobs cannot be reopened or have their result replaced. Retry a transient error before terminal failure, retaining the guest reservation.
- One active (`queued/processing`) conversion and one completed conversion per guest are enforced by partial unique indexes. Reservation IDs must reference that same guest's conversion. Trial-state fields must agree; a consumed marker cannot be reset by an update. Result expiry/deletion does not remove this marker.
- One unrevoked API key per user is enforced by a partial unique index; prefix lookup is unique separately. Rotate by revoking the current key and inserting its replacement in the same transaction.
- File soft deletion and physical deletion have distinct, consistent states: `present`, `pending`, `deleted`. Metadata remains linked to the conversion so both future download paths can deny access immediately. User/guest/file deletion is restricted while durable file/conversion records refer to them; no cascading file cleanup silently resets accounting. User settings/tokens/keys cascade only when their user can actually be deleted.
- Background intents have unique deduplication keys, object-shaped payloads, positive payload versions and nonnegative attempts. Leases are complete pairs; completed work has no active lease. Never persist plaintext credentials or uploaded content in payloads. Implemented notification intents store AES-256-GCM encrypted recipient/token material, authenticated by task ID/version; Redis jobs contain only the task ID. Completion/skipping clears ciphertext. VerificationToken stores only the token hash, purpose, bounded attempts and expiry.

## Implemented authentication transactions

Registration commits the user, default settings, verification token and encrypted email intent together. Resend and sensitive changes lock the user first, then update tokens, keeping a consistent lock order. Argon2id hashing/verification happens outside these short transactions; confirmed profile/password writes re-check the credential hash and session version after taking the lock. SMTP and Redis/BullMQ operations never run while a database lock is held.

Token consumption re-reads purpose, expiry, attempts and consumption state under the same user lock. Invalid-secret attempts persist even when the HTTP result is an error. Exactly one concurrent consumer applies a password/email mutation. Password change/reset and confirmed email change increment `sessionVersion` and invalidate pending tokens in that transaction. Redis sessions contain the matching version; each authenticated request reads PostgreSQL, so another replica cannot retain old authorization through a local validity cache.

Notification workers claim `email_notification` tasks conditionally with a fresh lease and increment durable attempts. Completion/retry updates require that same unexpired lease. SMTP acceptance cannot be atomically committed with PostgreSQL, so delivery is at least once; duplicates use the same expiring, single-use token. Five attempts bound delivery retries; monitor failures and pending age. Other task types are not dispatched by this consumer.

## Implemented guest transactions

Guest bootstrap stores only a random opaque-token hash with a fixed database-clock expiry. Reuse never extends the credential or resets its state. Account sessions remain independent; owning guest credentials still resolve guest conversions after login without changing persisted ownership.

`GuestTrialService.reserve` takes the guest row lock, revalidates the principal hash/expiry and available trial, and requires a two-hour admission window. Its database-only callback creates input metadata, queued Conversion and durable dispatch intent before the same transaction reserves that conversion. Any failure rolls all these writes back. Existing partial indexes and reservation guards provide independent backstops.

Settlement always locks GuestSession before Conversion. Matching processing version/token and lease validity fence publication, retry and terminal failure. Completed output must be guest-owned, present and temporary with expiry exactly one hour after a fresh completion timestamp and no later than credential expiry. Result publication and irreversible consumption share the transaction; terminal failure releases only its matching reservation, while retry retains it. Duplicate terminal deliveries skip callbacks. Explicit expired-lease reconciliation can fail/requeue but cannot complete work. Future conversion workers must enforce the credential-expiry-minus-one-hour deadline; no conversion consumer is registered yet.

The helpers accept a caller-owned short transaction, with no Redis/object-storage/SMTP work under locks. No schema or migration changes were needed. `npm run test:guest` verifies these transactions on real PostgreSQL/Redis; production conversion/download adapters must still enforce ownership and file expiry/deletion on every read.

## Index rationale

| Access pattern                                  | Index                                                                                        |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Login, token and API-key lookup                 | Unique email, token hashes and API prefix.                                                   |
| Credential invalidation / expired-token cleanup | Verification token `(userId, purpose)` and `expiresAt`.                                      |
| API-key history and active-key rule             | `(userId, createdAt)` plus unique active-user partial index.                                 |
| Saved-file date pagination and type filter      | `(userId, createdAt, id)` and `(userId, format, createdAt, id)`; `id` breaks timestamp ties. |
| Guest-owned file lookup                         | `guestSessionId`.                                                                            |
| Conversion history / guest result lookup        | `(userId, createdAt)` and `(guestSessionId, createdAt)`.                                     |
| Reconciliation and worker recovery              | `(status, updatedAt)` plus processing-only `(leaseExpiresAt, id)`.                           |
| Output expiry and storage deletion              | Live temporary `(expiresAt, id)` and pending-deletion `(deletedAt, id)` partial indexes.     |
| Background dispatch/retries                     | Pending `(availableAt, id)`, pending leased `(leaseExpiresAt, id)` and `(type, resourceId)`. |

Source/result uniqueness prevents reusing an upload across accepted jobs or publishing one result for different conversions. No trigram index, row-level security or extra extension is introduced without workload/architecture evidence.

## Domain transaction requirements

Schema constraints are backstops. Authentication and guest helpers are implemented as described above. Future conversion/file adapters must wire the helpers into the transactions below; helpers alone do not process uploads or execute jobs.

1. Register user/settings together; hash and validate credentials outside long-held database locks. Consume a valid unexpired single-use token with a conditional update and apply its identity mutation atomically.
2. At acceptance, create input metadata, conversion and durable dispatch intent; reserve the available guest allowance with a conditional update in the same transaction. A unique active-job constraint alone does not authorize a consumed guest to upload. Snapshot account settings at acceptance; guest snapshots are always false.
3. Claim processing with a new lease token and incremented version. Publish only with a matching current lease/version, inserting the result, completing the job and consuming that exact guest reservation atomically. A version column alone does not fence stale workers.
4. Release only the matching reservation after terminal failure; transient retries retain it. Concurrent acceptance/reconciliation should use a consistent lock order and bounded transaction retries.
5. Commit soft deletion and a durable deletion intent together, then retry physical object removal. Enforce owner, deletion and expiry checks on every read before asynchronous cleanup. Keep consumed guest accounting beyond result cleanup and retain access to old guest results after login without changing ownership.
6. Do not perform storage, email or queue network operations while holding database locks. The durable intent/reconciler bridges PostgreSQL, Redis and object storage; there is no transaction spanning those systems.

## Commands, tests and deployment

```sh
npm run db:validate
npm run db:generate
npm run db:migrate:dev --workspace=@converter/backend -- --create-only --name descriptive_change
npm run db:migrate:deploy --workspace=@converter/backend
```

Review generated migrations and preserve custom SQL guards/indexes. Use `migrate dev` only against disposable development databases. Use `migrate deploy` as one release job after backup/recovery preparation, not in every API/worker replica. Do not use `db push` or schema resets to replace reviewed migration history. These commands target the CLI-configured `DATABASE_URL`; none runs automatically at application startup.

Run `npm run test:database` with an explicit `TEST_DATABASE_URL` for a dedicated loopback database named `converter_test` or `converter_test_<suffix>`. No environment file is loaded by this suite, and `DATABASE_URL` is never used as fallback.

```powershell
$env:TEST_DATABASE_URL = 'postgresql://converter_test:local-test-only@127.0.0.1:5432/converter_test'
npm run test:database
```

The suite creates a unique schema, executes the real migrations, checks valid/invalid writes and concurrent inserts through independent PostgreSQL connections, then drops only its own schema. It fails without the explicit test target. CI supplies disposable PostgreSQL 18 in a separate job; offline `test:all` stays independent of database availability. Tests establish schema behavior, not implemented authentication, API ownership checks, queue execution or conversion engines.
