# Clarity Converter — Improvement Plan

## Overview

Prepared 2026-11-07 (Europe/Paris), against branch `main`, commit `6c297a5`. This is a controlled, implementation-ready plan for improving the existing product. It authorizes no implementation, deployment, migration, service restart, quota reset, or subsequent plan edits.

The previous plan is [docs/implementation-plan.md](docs/implementation-plan.md), not `implement-plan.md`. Items 1–16 are marked complete there; verification item 17 and deployment item 18 remain open. Their markers are historical baseline information, not verification performed for this document. This phase builds on those features and overlaps their remaining verification concerns without completing or rewriting the previous plan.

Objectives: restore the owner's guest conversion flow; introduce the approved Clarity Converter name and Hero; improve navigation, registration/security and converter continuity; expand formats through existing engines; verify reliability, contracts and owner acceptance. Expected outcomes are understandable failures, authoritative quota accounting, consistent UI, a tested conversion matrix and explicit residual limitations.

Constraints and non-goals:

- Preserve the modular monolith, npm workspaces, existing dark visual identity, Ukrainian UI, `/api/v1`, current session/CSRF/ownership contracts and existing saved-file behavior.
- Preserve one successful guest conversion, failure release, acceptance-time account auto-save, temporary guest ownership and one-hour result availability. Authentication never transfers or saves a guest result.
- Retain the exact 20,000,000-byte input limit. No pricing, billing, batch upload, global redesign, PDF → DOCX, SVG output, GIF output or new conversion service is included.
- Do not rename internal packages, routes, environment variables, cookies, queues, database objects, repositories or infrastructure to match public branding.
- No destructive infrastructure testing, production fault injection, dependency installation or application-state changes belong to this planning task.
- Existing user work must remain intact. Future implementation must follow applicable repository instructions, including preserving existing tests when modifying functionality. Add separate essential regression tests; request explicit authorization if an existing test genuinely must change. Never weaken assertions to obtain a pass.

Phase Definition of Done: every agreed task has its acceptance evidence; guest success/failure/concurrency and all advertised conversion pairs pass real-engine acceptance; security boundaries and current MVP flows regress cleanly; relevant automated checks actually pass; available-browser/manual owner checks have recorded outcomes; documentation matches implemented contracts; release-blocking failures are resolved. Unavailable environments and deferred decisions remain explicitly blocked, never reported as passes. Owner-discovered issues enter an authorized follow-up cycle before release acceptance.
